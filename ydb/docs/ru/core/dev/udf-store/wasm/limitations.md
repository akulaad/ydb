# Ограничения WASM UDF

Ниже перечислены ограничения и типичные ошибки при работе с [WASM UDF](index.md). Каждое ограничение связано с текущей моделью исполнения (песочница WebAssembly на запрос и линковка библиотек). Как писать модули с sdk, без него и с `object_framework`, см. [Написание и сборка](writing.md).

## Конфигурация и доступность {#config}

- UDF Store и WASM по умолчанию выключены. Нужны `udf_store_config.enabled` и `enable_wasm_udf` — см. [конфигурацию](../../../reference/configuration/udf_store_config.md).
- Функции доступны в YQL только после `CompileStatus = "ready"`. Статус и текст ошибки — в [`.sys/udf_modules`](../../system-views.md#udf-modules).

## Библиотеки и аллокация {#libraries}

- Если модуль выделяет память через runtime, первая библиотека в `required_libraries` должна экспортировать рабочие `malloc` / `free`. Пустой stub sdk без `malloc` приводит к падению при аллокации.
- Пустой `required_libraries: []` подходит только узким сценариям без wasm-`malloc` (например, минимальная арифметика на целых). Пути со строками и результатами обычно требуют sdk.
- В одном запросе с несколькими WASM-модулями первая встреченная «первая» библиотека становится общим runtime. Разные sdk у разных модулей в одном запросе не поддерживаются предсказуемо — используйте общий runtime.

## Изоляция и состояние {#isolation}

- Состояние WASM (включая handles объектов TypeConfig) не разделяется между запросами: объект создаётся заново в каждом запросе.
- Handle TypeConfig валиден только в текущем запросе; нельзя сохранять его между запросами.

## Загрузка и имена {#upload}

- Повторная загрузка модуля с тем же `module_name` без удаления предыдущего приводит к конфликту имён в реестре. Сначала удалите старый модуль.
- Публичного продуктного CLI для upload пока нет; используйте tooling записи в таблицы store — см. [Управление модулями](../managing.md#upload).
